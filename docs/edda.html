The localDNS handbook

A keyboard-first field manual for the private networking stack running on an HP t630 thin client. Every subsystem in one place — searchable, fast, and faithful to the live box at 192.168.1.118.

Host · HP t630 · Ubuntu 24.04 DNS · Pi-hole → Unbound (DoT split) VPN · WireGuard wg0 Source of truth · the live t630

§0 What this repo is

A config snapshot and rollback target — not the running system itself.

This repository is the consolidated 2.0 snapshot of a home network server: recursive DNS, ad-blocking, a WireGuard VPN, link-quality tuning, uptime monitoring, and an optional LLM router. Every file here maps to a specific path on the live machine (see Deploy paths). Edits in the repo do not take effect until they are manually deployed.

◆ Invariant

The live t630 is the source of truth. When repo and box disagree, the box wins — SSH to 192.168.1.118 and reconcile. This repo exists so a clean Ubuntu 24.04 install can be rebuilt into a working system.

The stack is organized into four service categories rather than install order: core-network (DNS, firewall, VPN), performance (CAKE, GPU/CPU governors), monitoring (Uptime Kuma, cron probes), and user-services (remote desktop, console, AI orchestration).

§D DNS split — Unbound

One resolver, two paths: encrypted for streaming, private for everything else.

streaming-forward.conf is the single decision point. High-volume, low-sensitivity domains (Netflix, YouTube, Spotify, Steam…) are forwarded to Cloudflare over DNS-over-TLS (1.1.1.1@853#cloudflare-dns.com / 1.0.0.1, forward-tls-upstream: yes) so the ISP sees an encrypted channel instead of cleartext lookups. Everything else — banking, email, health, the default — resolves recursively with DNSSEC; Cloudflare never sees these queries.

⚠ Invariant

Never add sensitive domains to the forward path — that would hand Cloudflare your private lookups. The recursive path never forwards anywhere; that is what keeps it private.

forward-first: yes fails closed to recursion: if Cloudflare's :853 endpoints are unreachable (an ISP blocking DoT), the streaming domains fall back to recursive resolution instead of returning SERVFAIL.

§B·4 Pi-hole

Ad-blocking front door with a single upstream — Unbound.

Pi-hole runs network_mode: host and forwards every query to a single upstream, 127.0.0.1#5335 (Unbound on the host). It does no resolver selection of its own — the streaming/personal split lives entirely in Unbound. Under Pi-hole v6 this upstream is re-applied and locked on every start via FTLCONF_dns_upstreams, overriding whatever a stale pihole_data volume holds.

⚠ Invariant

Do not add public resolvers in Pi-hole. That would race them for all queries and leak personal lookups. A single upstream is what preserves the private path.

Why host networking? Ubuntu 24.04 uses nftables with a default-DROP INPUT chain, so Docker bridge addresses aren't reliably reachable for a host-loopback service like Unbound, and bridge published-ports insert DNAT that runs before UFW. Host networking removes the namespace boundary: Pi-hole reaches Unbound at 127.0.0.1:5335, its ports are gated by UFW, and it answers VPN peers on wg0 directly.

"Permit all origins" is checked — safe here because UFW restricts port 53 to 192.168.0.0/16 and 10.8.0.0/24. Without it, Pi-hole would refuse queries from 10.8.0.x VPN peers, which are not on the LAN subnet.

§B·7 WireGuard VPN

Tunnel home from anywhere — DNS, ad-blocking and DNSSEC come with you.

The t630 runs a WireGuard server on 51820/UDP. Peer DNS points at 10.8.0.1 (the wg0 interface), reachable because host-networked Pi-hole binds 0.0.0.0:53 on every interface including wg0. Phone DNS on cellular therefore flows through Pi-hole + Unbound identically to LAN.

Forwarding — UFW owns it, not raw iptables

The classic failure: a peer connects, ping 10.8.0.1 works but ping 1.1.1.1 fails. Raw -A FORWARD rules in wg0.conf PostUp land after UFW's DROP and are never reached. The fix is two changes:

  1. Remove FORWARD rules from wg0.conf PostUp — UFW owns the filter FORWARD chain.
  2. Set ufw default allow routed in 01-core-network/ufw/setup.sh.

MASQUERADE stays in PostUp — UFW does not manage the nat table, so that is its correct home.

⚠ IPv6 black hole

Peers set to AllowedIPs = 0.0.0.0/0, ::/0 handshake fine but pages hang: the server is IPv4-only in-tunnel, so IPv6 (which phones prefer) is dropped. Default peers to 0.0.0.0/0 only. The leak-free fix is a ULA prefix + NAT66 — see network-context.md.

§B·6 Firewall — UFW

Default-deny, with every service scoped to LAN + VPN.

UFW (01-core-network/ufw/setup.sh) is default-deny incoming. Every service is scoped to the LAN (192.168.0.0/16) and the WireGuard subnet (10.8.0.0/24) — except WireGuard's own 51820/udp, the single port open to Anywhere, because the phone handshakes from a public cellular IP.

Two interactions matter:

  • Forwarding for the VPN — ufw default allow routed passes peer traffic out enp1s0. Raw -A FORWARD rules do not work (see WireGuard above).
  • Host networking makes UFW effective for containers — because Pi-hole and Uptime Kuma are host-networked, their ports genuinely pass through UFW's INPUT chain, unlike bridge + published-ports where Docker DNAT bypassed it.
⚠ Never

Never port-forward the console web terminals (8088 / 7681 / 7682) or the admin UIs. They are a login shell over HTTP — remote access is through WireGuard, never the WAN.

§1·9 Performance — CAKE & GPU

Smart queuing for the traffic the box actually forwards, plus a headless-GPU fix.

CAKE / bufferbloat

CAKE rate-limits egress just below the ISP line speed so the OS queue — not the modem buffer — is the bottleneck, then applies fair queuing and DSCP priority so DNS and interactive traffic skip ahead of bulk transfers. cake-setup.sh marks every DNS response (source port 53) DSCP EF into CAKE's highest tin.

Because the t630 is not inline for general LAN traffic, CAKE only shapes what the box forwards — WireGuard VPN client traffic. Measured under load: upload holds at 11 ms, download 16 ms (idle 14 ms) — vs. ~400–800 ms unmanaged. Whole-network bufferbloat needs third-party firmware on the R7000 (FreshTomato / OpenWrt).

AMD Carrizo GPU downclock

The iGPU drops to ~200 MHz headless. Four pieces, all required:

  1. GRUB: amdgpu.dpm=1 amdgpu.runpm=0 processor.max_cstate=1
  2. gpu-performance.service
  3. cpu-performance.service
  4. 99-amdgpu-performance.rules — re-asserts high on every DRM event

✓ Diagnostic logic

If Pi-hole Full Chain goes red but Unbound Basic stays green, the break is in the Pi-hole → Unbound link, not Unbound. If both are red, Unbound is the problem.

◈ Gotcha

The DNS monitor's Resolver Server field takes an IP only — no port. Port goes in the separate Port field. 127.0.0.1:5335 in the resolver field creates an invalid double-port and fails intermittently.

§12·G AI orchestration

Route whole models, don't shard them — and never trust a single warm draw.

Route, not shard

A LiteLLM proxy gives the household one OpenAI-compatible endpoint (ai.home.lan:4040 — 4040 because NoMachine owns 4000) that routes to whole-model backends: local Ollama by default, a cloud tier as overflow. Open WebUI (chat.home.lan:3000) is the browser front-end and talks only to the router.

Sharding a model's layers across machines loses to physics: inference is sequential and latency-bound, and a gigabit hop is thousands of times slower than the interconnect inside one box. So the felt experience — "use the best resource, adapt when a machine goes away" — is delivered as health-checked failover between whole endpoints, which LiteLLM does natively.

The Jury — LLM sampling doctrine

How the stack drives its own models. The unit of inference is one tuned draw; reliability comes from how many draws and how they're aggregated:

  • Lazy anchor — the first token is a cheap reflex (reasoning_effort: low), not a pre-committed conclusion.
  • Governed-warm body — warm enough to self-correct, always paired with a tail-clip (top_p/top_k) so it can't sample garbage. Default: temperature 1.1, top_p 0.9, top_k 40, penalties 0.
  • Concurrent vote — never consume a single warm draw for anything that matters. Sample several; let a plurality outvote the idiosyncratic ones.
◆ Invariants

Match every degree of temperature with a degree of governance. Temperature is a variance dial, not an intelligence dial. And measure p, don't guess it — voting only helps when the correct answer is already modal; below that it entrenches a wrong answer. Run jury.py calibrate on the task first.

The tool lives at 04-user-services/ai-orchestration/jury/ (adaptive sequential voter, stdlib-only, offline --mock mode), with a Claude-backend variant in jury-claude/.

§C Bring it up

Setup is interactive; deploys are staged.

The step-by-step build (Steps 0–11) lives in the reactive Interactive Field Guide — toggle your WAN config, enter your LAN IP / username / interface, and every terminal command on the page live-updates to your environment. It is not duplicated here on purpose: a single reactive wizard beats a stale copied guide.

Config that has been reconstructed or bug-fixed in the repo but not yet applied to the live box is staged, in dependency order with copy-paste commands and per-stage verification, in docs/DEPLOY-QUEUE.md — a runbook ready to execute the moment SSH to 192.168.1.118 is available.

◈ Working rule

Every commit to main must leave the repo able to reproduce a working system on clean Ubuntu 24.04. A file's real destination is the deploy table — don't infer it from the folder number.
