# M14 · tools/check-stop-hook.py

Question: list every defect in this file that could make a check or instruction silently fail or be read two ways. Quoted with file and line.

## Defects

- `tools/check-stop-hook.py` line 78: `return json.loads(r.stdout).get("reason", "") if r.stdout.strip() else ""`. An empty stdout is returned as "" and is read as "allow". A crashed hook, a hook that exits nonzero with no output, and a block that carries no `reason` key all look the same as an allow. The allow-case assertion on line 94 (`if want is None and got:`) then passes silently. Only the block-case assertions (line 96) would notice, and only because a crash also reads as allow there.
- `tools/check-stop-hook.py` lines 134 to 135: `if subprocess.run([...], input="not json", capture_output=True, text=True).stdout.strip(): fails.append("malformed input must fail open")`. The fail-open test checks only that stdout is empty. It ignores the exit code and stderr, so a hook that crashes with a traceback passes as "fail open". The call also has no `timeout=`, so a hung hook blocks the gate indefinitely instead of failing.
- `tools/check-stop-hook.py` line 112: `if "LANDING" not in run(box, reply):`. The other assertions use `startswith` (lines 96, 102, 115, 121, 127). This one uses substring `in`, so a LANDING assertion passes if the word appears anywhere in the reason, even when another rule blocked the reply. Read two ways: the same check means "this rule blocked" on line 102 and "this word appears somewhere" on line 112.
- `tools/check-stop-hook.py` line 115: `"DEC-900" not in got.split("\n\n")[-1]`. This tests the last paragraph of the reason only. If the hook puts a DEC item in an earlier paragraph, the assertion passes and the "DEC items must not start a sub-loop" rule is not checked. The test depends on the reason's paragraph layout, which the file does not pin.
- `tools/check-stop-hook.py` line 139: `if f'"{key}' not in hook_src:`. This is a substring test on the hook source. A key that appears only in a comment, a docstring, or an unused string counts as "enforced". The message on line 140 says "the hook does not enforce it", which the check cannot establish.
- `tools/check-stop-hook.py` line 141: `if phrase not in style:`. Same substring weakness on the output style. A phrase that sits in a quotation or a code sample counts as "the output style says it".
- `tools/check-stop-hook.py` lines 53 to 65 and 136 to 139: the rule list `STYLE` is hand-maintained. The docstring (lines 4 to 7) says "every rule the hook enforces must be named in .claude/output-styles/briefing.md". The code checks only the keys listed in `STYLE`. A rule the hook enforces but nobody adds to `STYLE` is never checked against the style or the retrofit table. The docstring overstates what the check covers.
- `tools/check-stop-hook.py` lines 143 to 148: `table = matrix_src.split("RETROFIT = {", 1)[-1].split("}", 1)[0]`. The table is cut at the first `}` after the marker. A `}` inside a value truncates the table, and keys after it are reported as "no retrofit entry" (a false failure, loud but misleading). Line 147 `f'"{key}":' not in table` also matches a key inside a comment in the table.
- `tools/check-stop-hook.py` line 149: `tested = {want for _, _, want in CASES if want} | {"SCRATCHPAD", "LANDING", "NEXT ACTION", "L ITEMS OPEN", "L STEP"}`. The five names after `|` are typed in by hand. The check on lines 150 to 152 ("has a blocking test case") therefore passes for those five even if the ad-hoc tests on lines 102 to 133 are removed. The check cannot fail for them.
- `tools/check-stop-hook.py` lines 129, 117, 119, 132: these assertions use truthiness (`if run(...)`). They inherit the empty-string-as-allow defect from line 78. A block with an empty reason cannot be seen.
- `tools/check-stop-hook.py` lines 98 and 108: `os.environ["MATRIX_SCRATCH_DIR"] = ...` changes the parent process environment. If anything between lines 98 and 108 raises, the variable stays set for the rest of the process. The `del` on line 108 is not in a `finally`. Minor, but the state is not restored on failure.
- `tools/check-stop-hook.py` lines 42 and 35 to 41 (case strings): the rehearsal record is written in lines 89 to 91 with the SHA-256 of the exact command text. The "REHEARSE" cases (lines 39 and 41) pass only if the hook hashes the same bytes. A hook that normalizes whitespace or the `cd` line would make the "rehearsed" case block (loud), but a hook that skips the rehearsal lookup entirely and always allows would fail only the block case. The record format is not checked anywhere in this file.

## Notes

The `CASES` table (lines 26 to 50) and the scratchpad, landing, tile and L-step cases (lines 98 to 133) cover the rules named in the docstring. Each case appends the `LAND` line (line 68) so that a single rule is under test. Lines 109 to 111 deliberately leave `LAND` off to test its absence.

The header on line 1 says the file writes a one-reply transcript in a temporary directory. Lines 71 to 77 write the transcript and pass `transcript_path` and `stop_hook_active` on stdin, which matches the hook's contract as the file expresses it. The hook source (`.claude/hooks/decide-act.py`) was not read for this report, so every claim about what the hook does is unverified against it.

The phrases on lines 54 to 64 (for example "lead state word", "Run the queue", "Landed · N =") are not checked against `.claude/output-styles/briefing.md` in this report. They are the strings this file expects that file to contain.

Line 20 builds the code fence from backticks so the file never holds one. That is intended and is not a defect.
