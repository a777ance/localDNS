# M13 · tools/check-registers.py

Question: list every defect in this file that could make a check or instruction silently fail or be read two ways. Quoted with file and line.

## Defects

- `tools/check-registers.py` line 26: `re.finditer(r"^## (%s-(\d{3})) · (.*)$" % prefix, ...)` only matches a level-2 heading with exactly three digits and the middle dot `·`. An entry written as `### INIT-005 · ...`, `## INIT-1000 · ...`, or with another separator is skipped without any message. It then drops out of the count (line 51), the duplicate check (line 30), and the newest-first check (line 32). The only failure path is "no entries found" (line 28), which fires only when every entry is skipped.
- `tools/check-registers.py` line 39: `body = text[h.end():heads[i + 1].start() if i + 1 < len(heads) else len(text)]`. The last entry's body runs to the end of the file, so any later non-entry section (for example a `## Notes` block that mentions `DEC-` or `blocked.md`) counts as that entry's body. A last entry marked `Blocked` with no real DEC id then passes the check on line 40.
- `tools/check-registers.py` line 40: `re.search(r"DEC-\d{3}|blocked\.md", body)` accepts any mention of a DEC id anywhere in the body, including one that does not explain the blocker. The check tests that a reference exists, not that it names the unblocker. Read two ways: the message on line 41 says "names no DEC id and no blocked.md entry", and a reader may take that as "names what unblocks it".
- `tools/check-registers.py` line 36: `status = h.group(3).rsplit("·", 1)[-1].strip()` takes the text after the last `·` in the heading, and the title on line 26 is `(.*)`, so a title may carry its own `·`. The status is still read from the last field, which is the intended reading, but the file never states that rule, so an author who expects the status after the first `·` gets a different answer with no warning. Read two ways: the heading format is not documented in this file.
- `tools/check-registers.py` line 32: `if nums != sorted(nums, reverse=True)` checks order on the numbers only. It does not say which entry is out of place, so the message on line 33 ("entries are not newest first") cannot be acted on. Not silent, but ambiguous.

## Notes
