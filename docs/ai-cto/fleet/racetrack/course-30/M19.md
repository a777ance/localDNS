## Defects

- tools/racetrack_plan.py line 27: the docstring of stage_cost says "Returns (tokens, seconds)" without saying that seconds is the slowest agent's time (the max, as line 36 computes it), not a sum. A reader can take the second value as total agent time, which is the other reading of the same return.
- tools/racetrack_plan.py line 30: "tokens = secs = 0" initialises a variable named secs that is never read or updated again (the loop at lines 32-36 only sums tokens and takes the max into worst). The name suggests seconds are summed alongside tokens, which contradicts line 36 and silently misleads anyone editing the function.

## Notes

The docstring at lines 4-8 says the constants come from "the measured v2 and v3 races (see RESULTS.md)". RESULTS.md was not opened for this milestone, so the constants A, B, T0 and T are not checked against it here.

Line 58 applies min(k, i - j) to agents, but line 54 already caps k at i - j, so the min is redundant. It does no harm.

Line 28 clamps k to lanes silently. Callers never pass k above lanes, so this does not change any result.

The word "lanes" means milestones in main() (line 76 help text: "roadmap length in milestones (lanes)") and means the work units of a single stage in stage_cost and agent_cost. The two uses agree because a lane is one milestone, but the word is overloaded and no line states that.

Ties in plan() (line 69) are resolved by min() on seconds alone. The Pareto filter at lines 60-65 has already dropped any course with equal seconds and more tokens, so the result is the same as the docstring's "shortest wall time" rule.

The Pareto filter at lines 60-65 keeps only courses whose seconds strictly fall as tokens rise. Adding a stage adds the same (tokens, seconds) to every course in a front, so dominance is preserved and pruning per milestone is sound.
