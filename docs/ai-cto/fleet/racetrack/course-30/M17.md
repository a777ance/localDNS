# M17 · tools/check-bridge.py

## Defects

- tools/check-bridge.py line 14: `if __name__ == "__main__":` wraps the only check call, so importing the module runs nothing and returns nothing. A caller that imports it to run the gate gets no exception and no failure, and the gate passes silently.
- tools/check-bridge.py lines 4-6: the docstring says this file draws every panel at four widths, framed and unframed, in colour and plain, and fails on overflow or colour leaks. The file does none of that. It only runs tools/bridge.py with --check (line 15). A reader who trusts the docstring would believe these checks live here, when they live in tools/bridge.py.

## Notes

The file is a thin wrapper. Its whole behaviour is line 15: it runs the interpreter on tools/bridge.py with the argument --check, with the repository root as the working directory, and exits with that process's return code. Whether the gate is real therefore depends on tools/bridge.py, which exists in the repository (confirmed by a file search) but was not read for this milestone. The claim that --check exits non-zero on a failing panel is unverified here.

If tools/bridge.py ignores unknown arguments, or exits 0 when --check is not recognised, this wrapper would pass silently. Reading tools/bridge.py's argument parsing and exit paths would settle it.

The subprocess call on line 15 has no timeout. A hung display check would hang the gate with no message. This is a robustness gap, not a silent failure, so it is not counted as a defect.

The subprocess inherits stdout and stderr, so a failing panel's message reaches the terminal. Nothing in this file swallows output.
